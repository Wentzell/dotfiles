Surface and fix the compiler & deprecation warnings of the **current** repo (a TRIQS app or
core-lib with a `c++/` tree). Typical use: just before a release, or after a TRIQS / nda / h5
bump that deprecated something. Run from the repo root.

These projects build with `-Wall -Wextra -Wfloat-conversion -Wpedantic …` but **no `-Werror`**
(an `${PROJECT_NAME}_warnings` interface target), so warnings don't break the build — they
accumulate silently until someone looks. This skill is that look.

## Argument

`$ARGUMENTS` (optional): build directory. Defaults to `build`. **Never `rm -rf <build-dir>`**
(it's usually a symlink onto local disk) — clear with `rm -rf <build-dir>/*` if you must reconfigure.

## Context

- Repo: !`basename "$(git rev-parse --show-toplevel)"`
- Has `c++/`: !`test -d c++ && echo yes || echo "NO"`
- Warning flags: !`grep -nE '_warnings\b|-Wall|-Wextra|-Wfloat-conversion|-Wpedantic|-Werror' CMakeLists.txt | head`
- `find_package(TRIQS …)`: !`grep -m1 -iE "find_package\(TRIQS" CMakeLists.txt || echo "(none — core-lib, builds standalone)"`
- Working tree: !`git status --porcelain | head`
- Build dir (default `build`) resolves: !`bd=build; if [ -d "$bd" ]; then echo "ok ($bd)"; elif [ -L "$bd" ]; then echo "DANGLING SYMLINK ($bd → $(readlink "$bd")) — recreate the target dir before configuring"; else echo "absent (fresh configure)"; fi`

If **no `c++/`** (pure-Python app — `maxent`, `dft_tools`, …): there is nothing to compile and
no warnings to fix. Report that and stop.

## Phase 1 — Build, capturing warnings

**Prefer the repo's existing build dir** (it already carries the repo-specific configure flags).
If the build dir is a **dangling symlink** (its local-disk target was deleted — see Context),
recreate the target first (`mkdir -p "$(readlink <build-dir>)"`); configuring into a dangling
symlink fails with a confusing `Unable to (re)create the private pkgRedirects directory` error
rather than an obvious "missing directory".
If you must configure fresh, use the repo's normal flags, not a bare command — some repos need
`-DCMAKE_INSTALL_PREFIX=…` (FATAL_ERROR otherwise, e.g. `h5`), apps need a matching TRIQS install
on `CMAKE_PREFIX_PATH` / `PYTHONPATH` (the `find_package(TRIQS major.minor)` check FATAL_ERRORs
otherwise); core-libs build standalone. Export compile commands so warnings attribute to files
precisely:

```bash
cmake -S . -B <build-dir> -GNinja -DCMAKE_EXPORT_COMPILE_COMMANDS=ON [-DCMAKE_INSTALL_PREFIX=…]
```

Build from clean object state so warnings actually re-emit (a cached build only re-warns on
recompiled TUs — touch nothing, but know a no-op build shows no warnings). Tee **all** output to
your session **scratchpad** (not a path in the repo, not a fixed `/tmp` file):

```bash
cmake --build <build-dir> 2>&1 | tee <scratchpad>/warnings.log
```

The build completes despite warnings (no `-Werror`). If it fails to **compile**, that's an
error, not a warning — stop and report it (or hand off to `/ci-triage` if it mirrors a CI break).

## Phase 2 — Parse & group

Extract the warnings and group them two ways so the work is tractable:

```bash
grep -nE 'warning:' <scratchpad>/warnings.log
```

- **By flag** (`[-Wdeprecated-declarations]`, `[-Wfloat-conversion]`, `[-Wshadow]`, …) — fixes
  for one flag tend to be uniform.
- **By owning file**, and crucially **app-owned vs dependency**:
  - **App-owned** — paths under this repo's `c++/<name>/` (and `python/**` generated includes
    that originate from app sources). **In scope.**
  - **Dependency** — warnings in TRIQS / nda / h5 / itertools / system headers pulled in
    transitively. **Out of scope** — you don't fix upstream headers here; list them in the report.
- **Never edit `*.wrap.cxx` / `*.wrap.hxx`** — generated by clair-c2py; if a generated file warns,
  the fix (if any) belongs in the C++ source/annotation and a `/regen-bindings` pass, not here.

## Phase 3 — Fix the app-owned warnings in-tree

Surgical edits to the app's own sources. Common cases in this ecosystem:
- **Deprecations** (`-Wdeprecated-declarations`): a TRIQS/nda/h5 API was renamed or replaced —
  switch to the new spelling (the same drift the porting script / `/release-changelog` migration
  notes describe; e.g. `mpi::monitor` method renames, mesh/nda API moves).
- **`-Wfloat-conversion` / sign / shadow**: narrow the conversion explicitly or rename the shadow;
  don't suppress with a pragma unless the warning is genuinely spurious and you say why.

Match surrounding style; change only lines the warning points at. Don't refactor adjacent code.

## Phase 4 — Rebuild & confirm

```bash
cmake --build <build-dir> 2>&1 | tee <scratchpad>/warnings-after.log
grep -cE 'warning:' <scratchpad>/warnings.log <scratchpad>/warnings-after.log
```

Confirm the app-owned warnings you targeted are gone and you introduced no new ones. Remaining
counts should be only the out-of-scope dependency warnings.

## Report

- Warnings before → after (counts), and the by-flag breakdown you addressed.
- App-owned fixes: `file:line` list with the one-line reason each.
- Remaining **dependency** warnings (out of scope) — file + flag, grouped.
- Reminder: **edits are uncommitted, and this skill does not run `ctest`** — build & test (a
  `/commit` follow-up runs clang-format + tests) before relying on the changes. Push is yours.
- **clang-format caution:** if the repo's sources are **not** already clang-format-clean (some, e.g.
  `tprf`, aren't), a blanket `/commit` format pass reformats whole files and **buries your surgical
  warning fix under hundreds of unrelated reformatting lines** — violating surgical-changes. Format
  only the changed lines (e.g. `git clang-format` against the pre-edit state) or skip formatting;
  never whole-file reformat a non-conformant file just to land a few-line fix.
